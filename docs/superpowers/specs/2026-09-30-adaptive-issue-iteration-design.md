# 自适应 issue 迭代与简短用量展示

日期：2026-09-30
状态：设计与实施计划已确认，代码已实现并通过离线验证；未提交，未进行真实服务试跑。

## 1. 目标与已确认约束

目标是改善 Symphony 自动开发、独立审查和返工之间的连续性，而不是让某一个功能在固定三次审查内通过。实现者和 reviewer 应主动推导不变量、风险及反例；用户不需要提前列出所有边界情况。

已确认的产品行为：

- 继续用 GitHub 保存交接和审查过程。Issue 保留完整信息，不依赖 PR 中的正文才能接手；不新增仓库内的逐 issue 工作文档、外部共享档案或记忆服务。
- 一个授权周期只有一个任务级总额度：20 次实际启动的 agent 会话。实现和 review 各消耗一次，不是 20 个实现—审查循环；SDK 会话成功创建后才计数。
- 启动前失败不扣次数，由宿主说明失败阶段并进入 Blocked，不无限自动重试。
- 移除单会话和跨会话费用阈值。费用在 issue 消息中供人查看，不驱动自动停止；暂不新增绝对运行时长限制。
- Reviewer 判断修复进展并提供依据，Symphony 用确定性代码执行继续／停止规则；不增加总控、总结或裁判 LLM。
- 明确需要人工决策或授权时立即交接；连续两次实际返工经审查确认无实质进展时暂停；达到总额度后不再启动 agent。
- 待开始（当前看板为 Todo）是人工启动／重新授权入口。进行中、返工、AI 审查由调度器管理，人不手动移入或移出；这是 onboarding 时告知的工作约定，不实现操作者识别或人工移卡监管。
- 人工在收到 Blocked 或 Human Review 的交接后，将卡片移回待开始，获得新额度；保留已有代码、分支、PR、历史和累计费用。
- 人工 merge／close issue 后进入终态，不扩展终态重新开工流程。
- 不再发布独立的用量评论。正常情况下，在 issue 的开发和 review 结果消息末尾附一行；获取或补写失败就跳过、记日志，不影响交接：

> 用量（本轮）：12.34 · 轮次 6/20 · 模型：xxxx

本规范落实已确认的产品取舍；字段命名和实现边界随修订稿一并审核。文档修订不等于允许实现，仍需批准后续实现计划。此前“不提交”的要求继续有效。

## 2. 当前实现与范围

当前调度器在 [src/orchestrator.ts](../../../src/orchestrator.ts) 中同时检查会话额度和费用，在卡片离开活跃列后关闭账本周期；[src/tracker/github-project.ts](../../../src/tracker/github-project.ts) 又按独立审查轮数强制交接。该组合会使提高审查轮数仍受较小会话上限影响，也可能在自动冲突恢复时开启新额度。

[src/ledger.ts](../../../src/ledger.ts) 目前保存当前周期的用量和暂停原因，没有保留人工等待期间的完整调度状态。[src/runner.ts](../../../src/runner.ts) 在会话结束时取得最终 SDK 用量；开发／审查消息通常此前已经发布。调度器随后单独发表用量评论。

当前会话计数已发生在 SDK 会话创建成功后，保留这一边界，修正启动前失败会持续重试的问题。实现者已有“说明阻塞、移到 Blocked、停止”的提示；reviewer 只有“评论并停止”的提示却没有对应状态出口，需补齐。

已有、尚未提交的完整上下文分页、阻塞反馈保留、临时长输出权限、主动验证提示词和 reviewer 临时反例测试改进是本设计的基础，不删除或覆盖。

本次不做：跨主机协调、操作者审计或人工移卡监管、findings 数据库、reviewer 实现代码提交、新的恢复命令、终态重新开工、定期强制 reviewer 介入、绝对时长上限、用量尾行持久化重试队列、历史评论批量改写，以及无关重构。没有证据表明换用文件就能提高缺陷发现率，因此不更换共享介质。

## 3. 状态所有权与恢复

### 3.1 看板约定

| 列 | 所有权与含义 | 对额度的影响 |
| --- | --- | --- |
| 待开始 / Todo | 人工授权入口；新任务也从这里进入 | 每次有效的新授权重置一次 |
| 进行中 / In Progress | 调度器派发实现者，或继续未完成的实现 | 不重置 |
| 返工 / Rework | 调度器根据 review 或合并冲突安排继续修复 | 不重置 |
| AI 审查 / AI Review | 调度器派发独立 reviewer | 不重置 |
| 人工审查 / Human Review | 自动工作已经交接，人决定验收、合并或重新授权 | 保留计数 |
| 阻塞 / Blocked | 启动失败、需要人处理、无进展或额度耗尽 | 保留计数 |
| 终态 / Done、Canceled | 人工 merge／close issue 后结束，按现有规则清理 checkout | 不删除已知累计用量，不自动重新授权 |

“调度器管理”包括 agent 通过宿主注册的受限 tracker 工具发起的合法交接，并不意味着调度器自行判断内容。人不使用运行中的三列作为恢复或暂停按钮；紧急停止通过停止服务处理。

这是一条在 onboarding 明确说明的工作约定，不是 GitHub 权限锁。程序检查角色、合法转换和额度，不鉴别人还是外部自动化拖动了卡片，也不保证识别“人工模仿合法转换”。其他自动化若把已交接的卡片放回待开始，也会构成重新授权；不要求关闭所有 GitHub 原生工作流。

### 3.2 一次授权只消费一次

- 首次发现符合标签等派发条件的新卡在待开始，创建授权周期。
- 已有卡只有从已记录的人工等待状态重新进入待开始，才建立新周期，调用数归零、停滞计数归零、解除暂停。
- Symphony 在启动 agent 前将卡片移到进行中。先持久化本次授权已消费及目标状态；状态更新失败时只重试同一交接，不重复授权。消费启动授权不等于扣除一次 agent 调用。
- 卡片持续停在待开始、重复轮询、自动重试、服务重启、移除后重新添加标签都不是新的授权。
- 首次接管时已经在进行中、返工或 AI 审查且无可恢复账本的卡片，不自动发放新额度。报告需要从人工等待状态重新进入待开始。
- 账本不再因为卡片离开活跃列就删除。授权标识、已用次数和等待原因跨重启保留。

保留现有状态协调：卡片进入终态或不再可执行时停止旧调用，合法角色交接启动新角色。同角色的合法转换不因无法识别操作者而被判非法；不增加通用移卡监管机制。运行列之间移动不重置额度，运行中移回 Todo 也不是受支持的重新授权入口。未能匹配有效授权时不直接派发或清零。

暂停记录先在本地生效。若 GitHub 状态更新失败，不因远程仍在活跃列就重新派发；恢复关键交接前核对当前状态，不覆盖已经发生的终态。人工合并／关闭 issue 后停止并清理，不为终态增加恢复分支。

轮询无法看到两次检查之间发生又被撤销的移动。人工应将卡片留在待开始，等待调度器接管，不依赖快速来回拖动。没有观察到的变化不猜测为授权。

### 3.3 自动冲突恢复

只有已正常交给人工验收、未被暂停且仍有剩余额度的任务，才可沿用现有合并冲突恢复进入 Rework。恢复沿用原周期及历史，不清零。

额度已耗尽、因无进展停下或明确要求人工决策的任务，不得被冲突恢复重新启动。第 20 次调用完成后若仍需修复，保持停止并告知移回待开始的恢复方法。

## 4. 20 次调用的计数

一次调用是一个成功创建的实现者或 reviewer SDK 会话，以 `createSession()` 成功返回为边界，对应当前的 `session_started`。启动 CLI 进程、派发 worker、准备工作区均不单独计数；同一会话内的模型请求、工具调用和 continuation turns 也不分别计数。

| 情况 | 计数和处理 |
| --- | --- |
| 工作区、依赖安装或初始化脚本失败 | 不计数；说明失败阶段并进入 Blocked |
| CLI 启动、连接或 SDK 会话创建失败 | 未成功创建会话则不计数；清理后进入 Blocked |
| 会话成功创建后首个请求失败、超时或中断 | 已计一次，不返还；未完成任务的后续会话受剩余额度约束 |
| 轮询、等待并发槽位、恢复关键消息或状态交接 | 不启动 agent，不计数 |

启动前失败直接暂停，不再通过无限重试绕开计数，也不引入另一套启动重试额度。宿主记录失败阶段和错误，人工修复后移回待开始。此时尚无 agent，不能等待提示词要求它自行报告或退出。

创建前检查剩余额度并记录本次启动身份；成功创建后按会话身份只计一次并保存，再发送工作提示词。记录启动身份不预扣额度。保存失败时停止执行，不能只记日志后继续工作。启动超时或崩溃留下不确定结果时，先核对并清理可能晚到的会话；不得立即再启动，也不能把未知状态当作一次已确认失败或成功。确认创建成功的会话结算一次，无法确认则保持暂停交给人处理。

- 第 20 次调用可正常完成工作、审查和结果发布；禁止第 21 次调用。
- 第 20 次通过审查时正常交给 Human Review，不把成功结果改写为失败。
- 第 20 次是实现且需要审查时，明确“最新修改尚未审查”，不额外赠送 reviewer 调用。
- 费用的实时事件与结束时指标合并去重，按调用保存，汇总至周期和 issue。人工重新授权不清除累计统计。
- 会话成功创建时固定其序号和周期；延迟到达的结果或用量只能归属原调用，不能污染新周期。
- 保留现有启动／hook 超时、运行中的无活动超时、stall 检测、并发控制、权限和 `max_turns`。不新增绝对运行时长限制；持续产生事件的 agent 可能长时间留在一次调用中。20 次限制启动次数，不保证总时长或总费用。

## 5. Reviewer 判断，宿主执行

### 5.1 区分代码结论与迭代判断

扩展现有 review 提交协议，而不是让宿主解析评论文字。Reviewer 提交：

| 字段 | 含义 |
| --- | --- |
| `verdict` | `approve`、`request_changes` 或 `unable_to_verify`；最后一种不伪造缺陷或通过结论 |
| `reviewed_head` | `approve`／`request_changes` 必须提供实际检查的 commit SHA；无法取得 SHA 的 `unable_to_verify` 可以为空并说明原因 |
| `progress` | `initial`、`made_progress`、`no_progress` 或 `not_assessed` |
| `progress_reason` | 可验证的修复变化，或无进展的具体依据 |
| `next_action` | 非批准结果必填：`continue` 或 `human_required`；批准结果不填写 |
| `next_step` | 非批准结果的下一步准备改变的方法，或需要人回答／授权的事项 |
| `summary`、`blocking_issues` | 完整审查记录和阻塞问题，继续使用现有记录渠道 |

宿主提供前次审查和待评估返工的标识，不让 reviewer 自行决定是不是首次审查。首次提交、单纯重试 reviewer、同一返工的重复工具调用都不能增加“无进展返工”次数。

宿主校验字段组合、调用归属、相应返工是否存在以及当前 PR head。它不能验证语义正确性；字段完整、测试全绿或问题数量减少都不自动证明有进展。没有有效字段时返回工具错误供同一调用纠正；调用结束仍无有效结果时按未完成／运行故障处理，不能默认批准。

`approve` 不得携带阻塞问题或要求先由人解决的事项；`request_changes` 必须包含真实阻塞问题。`unable_to_verify` 用于无法作出有效质量判断且需要人提供条件的情况，使用 `progress=not_assessed`、`next_action=human_required`，由宿主发布完整原因并进入 Blocked。缺失被审 SHA 时不捏造，也不将该结果当作对某个版本的质量结论。已启动会话中的短暂运行故障按运行故障处理，不伪造完成的 review。

补齐 reviewer 的有效退出口径：不能只是“评论并停止”，却让卡片留在 AI Review 继续被续跑。它应提交上述阻塞结果，宿主确认交接后结束当前调用；不开放任意状态修改或实现代码提交权限。

实现者保留“说明阻塞、移到 Blocked、停止”的路径，并明确：现有工具和权限内可解决的依赖或测试失败继续处理；必要凭据、外部服务或环境能力缺失，或者有证据确认无法在任务约束内实现时，说明尝试、证据和需要人的具体行动后退出。仅仅实现困难不构成自动放弃理由。

### 5.2 决策规则

按以下含义处理合法结果，任何“继续”仍受剩余额度约束：

1. 审查通过且没有阻塞或必要的未验证项：交给 Human Review，不自动合并。
2. 明确缺少人工决策、访问授权或外部必要条件：立即交给 Blocked，说明人需要做什么，不要求重复投停止票。
3. 有已确认缺陷，返工取得实质进展：清零连续无进展次数，继续 Rework。
4. 第一次经审查确认的无进展返工：记一次，给一次改变方法的机会；交接必须说明下一步区别于已失败方法的尝试。
5. 连续第二次实际返工仍经审查确认无进展：交给 Blocked，保留剩余问题及两次尝试的依据。
6. 无剩余额度而工作未完成：交给 Blocked，不再启动 agent。

初次审查发现阻塞但有可执行的修复方向、无需人工介入时进入 Rework，不增加无进展计数。SDK／网络／工具运行故障不算语义停滞，也不清零已累计的停滞次数。未能验证的一轮不伪装成“有进展”；修复后恢复有效审查再继续评估。

“修好两个旧问题，又发现一个新问题”可以有进展。新增 commit、改动行数、单纯发现新问题或换一种说法均不单独算进展。排除重要错误假设必须有验证依据和不同的可执行下一步，不能靠空泛探索无限续跑。反复破坏已经验证的修复，需要 reviewer 在判断中明确指出。

如果旧 blocker 被证明不成立，应给出证据并更正，不为凑停滞次数坚持错误结论。所有语义判断仍由 agent 作出，最终人工验收仍然必要。

### 5.3 新代码、重试与重复结果

提交 review 时绑定 `reviewed_head`，核对当前 PR head；版本已变化时不把旧审查当成对新代码的批准。已完成结果使用调用标识去重；评论、状态更新或回调重试不得重复计入停滞或重复触发下一位 agent。

一次有效的请求修改开始一段返工，由实现者正式交接后的下一次有效审查结算一次。中间可以包含多个实现会话；不是每个会话都单独累加停滞。未产生新 commit 时也允许交接，但必须说明尝试及结果，reviewer 重新验证旧反例后才能判断无进展。对同一次返工重复审查不能累计两次。

实现者一直未交接时，不触发“经审查无进展”判断，只消耗实际启动会话的总额度；本次不增加定期强制审查或额外监工 agent。

未启用独立 review 的工作流仍使用同一调用额度、状态入口和用量规则；不伪造 reviewer 进展评估，提交后按原配置交给人。

## 6. GitHub 交接记录

### 6.1 内容由 agent 负责

实现交接说明：本次修改、验证的命令与结果、已失败方法及原因、仍存在的问题、建议下一步及提交版本。Review 记录说明：检查过的准则与不变量、反例和证据、旧问题的验证、新问题、未验证区域以及进展判断。

新调用先读最近实现交接、最近审查和新的人工反馈，再按需翻阅历史。继续使用完整正文和分页；不把第一页、摘要或已落盘但未读取的长输出当作完整上下文。

记录事实、结论、复现步骤和必要证据，不索取模型内部推理，不上传凭据，也不把整个会话原始日志贴到 GitHub。Reviewer 仍独立检查代码，不把实现者的“已修复”当作已验证事实。

### 6.2 Issue 保留完整信息

每次开发交接、review 结论和必要的阻塞说明都在 issue 保存完整正文，包括关键证据和下一步；链接到 PR 只是辅助，不代替内容。PR 继续用于代码审查和现有结果展示，接受正文适度重复，不在本次增加“issue 只留摘要链接”的优化。

即使 PR 关闭，后续 agent 也应能仅通过 issue 历史恢复 Symphony 已记录的开发和审查过程。PR 中新的人工反馈仍需读取；agent 将据此采取的行动、重要约束和处理结果写回 issue 交接。这里不承诺自动镜像所有人工评论。

不回写历史评论强制统一格式。保留完整正文及分页，只有重复内容的完整来源确实存在于当前响应时才去重；不能因用量尾行或正文格式变化而丢失唯一的阻塞反馈。保留临时长输出目录供 agent 读取原始工具结果，它不是长期共享记录。

## 7. 用量尾行

### 7.1 展示约定

正常情况下，在 issue 的开发和 review 结果消息末尾使用：

> 用量（本轮）：12.34 · 轮次 6/20 · 模型：xxxx

- 数值单位为 SDK AI credits，保留两位小数；不显示美元，也不增加 issue 累计值或 token 长表。
- “本轮”和“轮次”均指一次 agent 调用，不是完整实现—审查循环。
- 模型来自本调用的实际 usage/metrics。若使用多个模型，列出去重后的实际模型名；不以配置中的 `auto` 充当实际模型。
- 无法可靠取得用量或实际模型时跳过尾行，记录日志；不把缺失值当作 0，也不伪造最终统计。
- 模型调用数、tokens、时间、代码行数、周期与累计费用继续进入日志／账本，不单独发布用量消息。

### 7.2 正常补写，异常忽略

开发／review 消息通常先于最终 SDK 指标发布。当前调用保留自己发布的 issue 消息 ID，会话结束后补写一条尾行；不能从“最后一条评论”猜测更新对象。用标记替换本调用的尾行，避免重复追加，只改自己的区块，不整段覆盖正文或人工编辑。PR 镜像若也展示用量，遵循同样的尽力写入原则，不作为交接前提。

用量仅供人查看：获取失败、消息已删除、不能安全更新、网络错误或进程退出造成未补写时，跳过并记日志，不阻塞任务、不重新调用 agent、不发独立用量消息。无需为尾行持久化待补写队列，也不保证跨重启补齐。

调用失败且没有结果消息时，仍需发布有实际原因和下一步的故障／阻塞说明；有可靠用量就附尾行，没有则不附。不能为了展示费用额外制造一条无交接内容的消息。核心交接正文或状态发布失败与尾行失败不同，按第 8 节处理。

## 8. 组件与控制数据

保留现有组件分工，不建立第二套语义存储：

| 组件 | 本次职责变化 |
| --- | --- |
| [配置与校验](../../../src/config.ts)、[工作流检查](../../../src/check.ts) | 明确人工入口和运行列；只保留一个任务级调用额度；校验自动目标不能是待开始 |
| [调度器](../../../src/orchestrator.ts) | 消费授权、实际启动后计数、按结构化结果继续／暂停，处理启动失败和恢复 |
| [账本](../../../src/ledger.ts) | 保存跨重启的最小控制状态、累计用量和未完成核心交接；不保存工作文档或用量补写队列 |
| [运行器](../../../src/runner.ts) | 运行当前角色，传递调用身份与结果事件，收集实际用量；保留长输出隔离与清理 |
| [Tracker 接口](../../../src/tracker/types.ts)、[GitHub adapter](../../../src/tracker/github-project.ts) | 校验角色作用域、发布并定位消息、绑定审查版本、更新用量尾行和看板 |
| [上下文读取](../../../src/tracker/issue-context.ts) | Issue 完整正文和分页，辅以 PR 反馈；不承担 LLM 总结 |

账本只保留必要的 issue 身份、授权与会话计数、启动确认状态、当前阶段／暂停原因、返工评估关联和停滞次数、已知用量，以及尚未完成的核心交接。用会话身份防止重复计数，用结果标识防止同一次返工重复结算，不维护通用状态审计系统。

完整结果正文仅在等待发布时暂存，发布完成后由 GitHub 保存；本地保留恢复和去重所必需的引用、当前周期状态及累计数，不再维护一份逐轮语义档案。

不把 Project item ID 当成唯一长期 issue 身份；同一 issue 移出再加入看板仍匹配原控制记录。调用或授权标识只是去重和归属标识，不是复杂的内容版本系统。

单个 issue 同时只有一个活动调用。受限工具的结果必须匹配当前调用；取消被观察到后，不再接受该调用的新状态变更请求。已经发出的远程请求不能撤回，须先核对结果再继续交接。迟到的用量归入原调用，不改变新周期额度。核心控制记录保存失败时暂停，而非只记日志后继续。

合法的结构化提交被宿主接受并保存后，本次语义工作即完成。随后 issue 正文或状态交接失败，只恢复这些关键宿主动作，不因收尾错误重跑实现／审查。创建结果不明时用调用标识核对已有消息，恢复状态前核对最新看板；无法安全确认时暂停，不宣称本地与 GitHub 之间有原子事务。用量尾行不属于关键宿主动作，失败按第 7 节忽略。

保持现有单宿主、单工作流实例拥有对应账本和 workspace 的假设；跨进程同时控制同一 issue 不在本次范围内。

## 9. 配置、兼容与迁移

为保留自定义列名，新增明确的 `tracker.provider.start_state` 和 `tracker.provider.working_state` 映射。本项目分别为 Todo 和 In Progress；不通过数组第一项或英文名称猜测。它们不是新的额度或功能开关。

复用 `agent.max_sessions` 作为唯一总调用额度键，默认及本项目、示例均设为 20；字段说明为“每次授权内成功创建的 agent 会话数”。已开启周期固定其授权时的额度，配置热更新不暗中清零或扩充该周期；下一次有效待开始授权才采用新的配置值。

移除 `review.max_rounds`、`copilot.max_ai_credits` 和 `copilot.max_ai_credits_per_issue` 的执行语义及配置项。旧键不能静默忽略：启动和检查均给出迁移错误，防止用户误以为旧费用上限仍有效。根工作流、示例和 onboarding 同步迁移。审查序号可留作描述，但不再是第二种上限；旧模板变量 `max_review_rounds` 一并迁移。

保留 `agent.usage_comments` 作为是否展示尾行的开关，默认开启；不再允许它产生独立用量评论。关闭展示不关闭日志和计费统计，也不隐藏必要的失败／暂停说明。Onboarding 同时解释状态所有权、待开始重新授权、费用仅供人工审查，以及尾行可能因异常缺失。

校验要求：

- 待开始、进行中和审查列互不混用，待开始和进行中都是可路由列。
- 已有任务的 `agent_states`、提交目标、review 返工目标和自动冲突返回目标不能指向待开始。
- `blocked_state` 必须存在且不是活跃列；review 的通过列是人工等待列。Blocked 不参与自动冲突恢复。
- 新建 follow-up 可以放到待开始，但不能自动获得派发标签；这不是对已有卡的额度重置。
- 所有新状态映射在 schema、运行时校验、工作流检查、看板设置及中英文文档中一致。

账本格式做一次最小兼容迁移：旧的活动记录保留已知会话次数和费用，不清零；无法还原的旧审查进展不从评论猜测，停滞计数从新的有效评估开始。旧账本已经丢弃的历史费用不能凭空补齐，累计展示明确仅覆盖可用记录。稳定身份映射只能在读取到对应 issue 后完成；身份不明或状态矛盾时暂停，不派发。

升级无需重写历史 GitHub 评论。仍未完成且处于人工等待的旧任务若没有可恢复账本，不自动进行冲突恢复；人工移回待开始后以新授权接管。已由人工 merge／close 的终态任务不在本次恢复范围内。

## 10. 验证与验收

实现阶段至少执行 `npm run typecheck`、`npm test`、根工作流和示例的离线 `symphony check`。设计阶段不运行付费 agent、不移动真实看板、不发布评论。

测试必须覆盖下列行为，不只验证配置能解析：

1. 实现和 review 共用 20 次实际启动会话的额度；超过原三次 review 可以继续；禁止启动第 21 个会话。
2. 工作区准备、CLI 启动和会话创建失败不扣次数且进入 Blocked；创建成功后的首个请求失败计一次。超时、晚到结果和重复事件不导致重复计数或并行启动。
3. 首次 Todo 只授权一次；重复轮询、重启、同一次状态交接重试和移除再加标签不刷新额度。
4. Blocked／Human Review 回 Todo 重置调用和停滞次数，保留代码、历史、累计费用；移到 Rework 不重置。
5. 自动冲突返回沿用额度，不能唤醒已暂停任务或绕开总上限；有足够额度的正常等待任务仍可自动恢复。
6. 合法角色交接、旧 worker 延迟结束和旧工具请求不造成双派发或错记额度；不要求识别人工与调度器做出的相同合法移卡。人工 merge／close 后正常停止清理。
7. 无账本的运行列卡片、重加看板导致 item ID 改变、账本损坏／写失败不会静默获得新额度。
8. 首次 review 不算停滞；两次正式交接后经审查无进展的返工才停止；有效进展重置停滞，运行故障不增加或抹除它。未提交不强制审查，同 SHA 的真实返工可以结算且仅结算一次。
9. 同一次返工的 reviewer 重试、重复提交和部分发布失败只结算一次；过期 SHA 不批准最新代码。
10. 实现者和 reviewer 均可有效提交人工阻塞并离开运行态；reviewer 不因“只评论”而被重复续跑。缺失或矛盾结果不默认批准，无法取得 SHA 的阻塞可以报告；未启用 review 的配置仍工作。
11. 正常情况下 issue 的开发／review 消息恰好一条规定尾行，没有独立用量评论；消息 ID 对应正确调用，模型来自实际使用记录。
12. 最终 SDK 指标晚于提交时可补写，实时与最终用量不重复累计；用量或模型获取失败时跳过，不将缺失伪称为零。
13. 尾行补写失败、进程中断、消息被编辑／删除时不影响交接、不重跑 agent、不覆盖其他正文，也不创建持久化补写队列。关键结果已接受后的发布／状态失败不重复执行语义工作。
14. Issue 保存完整开发、review 和阻塞记录，PR 关闭后仍可读取；正文与分页兼容，原有长输出访问和清理测试持续通过。
15. 第 20 次为批准、请求修改或尚未审查的实现时，状态和文案准确；移除旧额度键、状态映射和模板迁移在运行时及离线检查中一致。

最终人工可见的成功标准是：一次任务能在完整历史基础上继续有价值的修复；停止原因能区分通过、需要人工、无进展和额度耗尽；人工只需从等待列移回待开始即可重新授权；issue 上不再出现独立的用量刷屏。

这不能保证 reviewer 发现全部缺陷，也不能保证 20 次调用内收敛。程序保证的是额度、状态、记录归属和交接规则，不是 LLM 判断一定正确。
